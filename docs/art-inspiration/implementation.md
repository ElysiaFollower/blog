# 实现路径与成本

这里比较方案，不规定必须安装什么库。评估以用户看到的能力为单位：需要变换视角、还是只需要固定镜头？需要连续弯曲、还是只需卡片旋转？风格探索先保留可能性，再据具体原型作决定。

## 仓库基线

2026-10-29 的源码检查显示：本站使用 Astro 静态输出与 MDX；依赖中已有 PhotoSwipe，没有 Three.js、GSAP 或全站客户端路由器。部署面向 GitHub Pages。现有组件使用 Astro 脚本、CSS、IntersectionObserver 和按事件请求的动画帧。

这是当前实现，不是永久技术限制。新库应解决具体表现力或维护问题，并尽量只随使用它的页面加载。不为一个 hover 效果整体替换页面框架，也不为了避免依赖而手写一套更脆弱的复杂动画系统。

相关入口：[Astro 配置](../../astro.config.mjs)、[依赖](../../package.json)、[交互文章约定](../interactive-articles.md)。

## 四种成本分别记录

1. **制作与维护：** 分镜、资产制作、建模、灯光、动画逻辑、设备适配与长期修改。代码短不等于制作便宜；光色和构图的调试可能比程序本身更费时间。
2. **资源分发：** 用户需要下载的图片、视频、模型、字体与脚本，以及缓存和按需加载后的流量。
3. **用户端运行：** JavaScript / 布局、GPU 绘制、媒体解码、内存、耗电，以及操作延迟。
4. **后端运行：** 请求计算、持久连接、状态同步与存储。不要把构建阶段或离线视频渲染的计算混入每次访问的服务端负载。

纯展示 3D 也可以静态托管：服务器分发资产，用户设备绘制画面，不必部署 GPU 服务器。CDN 可以降低源站压力，但不会消除对访客的资源传输。多人同步、在线推理或云端渲染才引入各自不同的后端需求。

例如“每次冷访问实际下载 8 MB，1 万次约 80 GB”仅是流量算术示例，不是本站测量值；实际应根据缓存、访问路径与加载策略计算。

## 方案对照

下表的低/中/高为合理实现下的相对工程判断，不是参考网站的实测分数，也不是工期或硬件承诺。

| 方案 | 可选技术 | 制作/维护 | 下载与分发 | 用户端运行 | 必需实时后端 |
| --- | --- | --- | --- | --- | --- |
| 排版、位移、透明度与简单转场 | CSS、Web Animations、GSAP | 低—中；精细编排仍需打磨 | 低，素材另算 | 通常低 | 无 |
| 多层视差与滚动时间线 | 分层资产、CSS scroll-driven animations 或 ScrollTrigger | 中 | 低—中 | 低—中 | 无 |
| 可拖拽的平面/空间画廊 | Pointer Events、DOM / CSS 3D、Draggable | 中 | 随图片数和尺寸变化 | 低—中 | 无 |
| 局部扭曲、水波、网格形变 | Canvas / WebGL、顶点或片元 shader | 中—高 | 低—中，依素材变化 | 中；全屏可能明显升高 | 无 |
| 简化模型与烘焙光照场景 | 建模工具、glTF、Three.js、烘焙贴图 | 高，重心在资产 | 中—高 | 中，依分辨率和场景变化 | 无 |
| 动态光照、阴影与多层后处理 | 实时 3D、反射、bloom 等 | 高—很高 | 不一定很大 | 中—高，GPU 风险突出 | 无 |
| 预渲染电影片段 | 离线渲染、原生 video | 中—高，成本前移到制作 | 中—高 | 通常低—中，仍需解码 | 无 |
| 滚动图像序列 | 分帧资产、Canvas、受限帧缓存 | 中—高 | 中—高 | 解码与内存风险突出 | 无 |
| 多人可漫游世界 | 3D 场景、角色/导航、WebSocket 状态同步 | 很高 | 资产与持续消息 | 中—高 | 有，按在线人数与同步方式增长 |

技术栏是候选，不是参考站的技术清单。浏览器原生 API 也需要按目标设备核对支持范围，并保留普通导航或静态内容路径。

## 三个需要单独决定的技术边界

### 真实 3D、2.5D 与视频

- 需要自由观察、动态遮挡或对象之间的空间互动时，实时 3D 有明确价值。
- 只需要少量前后层次与视差时，分层资产可能已经足够；大幅转动会暴露平面边界。
- 固定镜头演出可以预渲染，但视频频繁 seek 与普通连续播放不是同一性能条件；视频也未必在所有设备上更省电。
- 图像序列便于按进度选帧，但不能默认将所有全尺寸帧解码常驻。下载压缩体积与解码后内存是两回事。

选择替代路径时，要说明保留了什么、失去了什么。不能把视觉上明显不同的轻量替代品当成已经验证原设计。

### 页面内编排与跨页转场

本站目前是多页面静态站。章节内的编排可以局部实现；跨文档转场可评估原生 View Transition API，或在明确需要时评估客户端路由。单个漂亮转场不足以自动证明全站路由改造值得做。

跨页方案还要处理直接访问、浏览器返回、滚动位置、焦点、脚本清理与重复初始化。普通链接必须继续可用。新增路由机制时，应检查现有各组件的初始化假设，而不是只验证首页的一次跳转。

### 静态展示与实时服务

Samsy 的光色与多人在线是可拆分的能力。借鉴前者并不需要为博客增加多人服务。本站若新增用户状态保存、多人同步或模型 API，另行确认需求、托管和运维范围；这里没有预先批准这样的扩展。

## 负载应看什么

- **改变的属性：** transform / opacity 通常可走合成路径；持续布局、重绘、大面积模糊不因使用 CSS 就便宜。过多合成图层也会占内存。
- **绘制面积与分辨率：** Canvas 像素数约为 `CSS 宽 × CSS 高 × 渲染像素比²`。像素比 1 → 2 意味着四倍像素，不代表总 GPU 时间必然四倍。
- **绘制次数：** 阴影和后处理可能追加绘制与缓冲读写；多个实时灯光、反射、景深叠加需要具体测量。
- **资源展开后的大小：** 模型与贴图压缩减少下载，不必然同等减少解码后内存。纹理尺寸、格式、mipmap 和缓存策略要分别看。
- **运行范围与时长：** 入场时、拖动时、当前章节可见时和整个会话持续运行是不同成本。画面不变时优先停止不必要的逐帧工作；离开视口后暂停，离开页面时释放资源。

60 fps 对应约 16.7 ms 的帧间隔，120 fps 约 8.3 ms，页面不能独占整个时间。帧率之外还要看输入延迟、偶发长帧和内存增长。不要依据一次访问“感觉卡”就判定是服务器、某个库或 WebGL 的问题。

## 从原型进入正式页面时

风格比较阶段不用为每个想法先做性能工程。选定值得推进的表现后，用相同内容、窗口尺寸与设备条件比较原型和当前页面，并记录实际测试环境。

至少确认：首次进入与返回、快速/反向滚动、触屏与键盘核心操作、窄屏断行、减弱动态模式、资源加载失败或脚本不可用时的可读内容。对于持续渲染场景，再看离屏暂停与资源释放；对于明显卡顿，再用性能 trace 区分主线程、GPU、解码与网络等待。

重页面逐个查看，完成后关闭，不让多个 3D 原型同时占用用户设备。展示关键静帧之外，还要亲自运行主要交互；截图不能证明时序与手感正确。未经测量不要标注“已优化”“稳定 60 fps”。

运行仓库规定的适用检查；代码准备交付或提交时执行 `pnpm verify`。视觉验证与构建验证各自提供不同证据，不能互相替代。
