图片的宽和高明明就在文件里，为什么还要引入一个完整的图像处理库？

这个问题源于相册瀑布流。浏览器只有在图片加载后才知道它的比例，布局会因此反复跳动。若构建阶段能够取得尺寸，就可以提前保留空间，让图片在真正出现之前已经拥有正确的位置。

<Sidenote label="设计动机">
  这不是为了追求更少的依赖，而是为了让构建产物携带足够的布局信息。依赖数量只是结果。
</Sidenote>

## 我们究竟需要解析多少

目标不是解码像素，也不是验证整张图片。我们只需要回答三个问题：

1. 这是不是支持的图片格式？
2. 尺寸字段位于什么结构中？
3. 在输入损坏时，解析器能否明确失败？

<Callout title="边界">
  一个尺寸解析器不应该假装自己是图片解码器。它只承诺读取结构元数据，并对越界、截断与非法段长度保持警惕。
</Callout>

## PNG：固定位置的尺寸

PNG 文件从八字节签名开始，随后是若干 Chunk。规范要求第一个 Chunk 是 `IHDR`，宽高分别是其中两个四字节无符号整数。

```ts
function readPngSize(bytes: Uint8Array) {
  assertPngSignature(bytes.subarray(0, 8));
  assertChunkType(bytes.subarray(12, 16), "IHDR");

  return {
    width: readUint32BE(bytes, 16),
    height: readUint32BE(bytes, 20),
  };
}
```

只要完成边界检查，PNG 路径相当直接。真正麻烦的是 JPEG。

## JPEG：沿着 Marker 行走

JPEG 由一系列 Marker Segment 组成。尺寸位于某个 Start of Frame 段中，但它之前可能有 EXIF、量化表、注释和其他任意长度的数据。

所以算法不是寻找某个固定偏移，而是顺序扫描：

```ts
while (offset < bytes.length) {
  const marker = readNextMarker(bytes, offset);

  if (isStartOfFrame(marker.code)) {
    return readFrameSize(marker.payload);
  }

  offset = marker.nextOffset;
}
```

这里最容易遗漏的是填充字节、`0xFF00` 转义以及没有长度字段的 Restart Marker。一个对正常样本有效的实现，并不等于一个结构正确的解析器。

## 构建阶段缓存

本地图片可以直接读取文件头；远程图片则应优先使用 Range Request，只取得足够的前缀。解析成功后，把 URL、缓存校验信息和尺寸写入构建缓存。

| 输入 | 获取方式 | 缓存依据 |
| --- | --- | --- |
| 本地文件 | 文件前缀 | 路径、大小、修改时间 |
| 远程图片 | HTTP Range | URL、ETag、Last-Modified |
| 已知元数据 | 直接使用 | 内容清单版本 |

> 性能优化真正有价值的部分，往往不是让某个函数更快，而是让它根本不必再次运行。

## 回到页面

当尺寸成为内容数据的一部分，瀑布流不再依赖图片加载完成后的修补。浏览器第一次布局就能得到稳定结果，懒加载只负责节省带宽，不再承担纠正几何结构的职责。

这也是构建型博客的一个优势：许多原本发生在访客设备上的工作，可以提前完成一次，然后作为静态结果分发。
